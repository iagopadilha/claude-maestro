# Concerns

Short, evidence-based. Not a backlog.

## Size and concentration
- `engine/run_loop.py` was split (2,770 lines to about 740; `loop_io`, `claude_accounts`, `limit_waits`, `claude_turn`, `permission_denials`, `worktree_state`, `worktrees`, `auto_answers`, `turn_gates`, `preflight_checks`, `loop_cli` hold the rest), but `run_loop.py` still re-exports every moved name so tests can patch `run_loop.<name>`: a function that calls something tests replace has to stay there. `engine/loop_state.py` is about 850 lines.
- `plugin/skills/orchestrator/hooks/guard.py` is about 1,880 lines even after the SQL tokenizer, path normalization, git/gh lexer and egress checks moved to `guard_sql.py`, `guard_paths.py`, `guard_git.py` and `guard_egress.py` next to it (they must ship together). Split more before adding rules.

## Duplicated logic
- Credential layers are resolved twice, with the same 5-layer order, in two repos: the claude-dev-toolkit's `shared/testenv.py` (stdlib, used by the skills) and `app/backend/harness_backend/engine/credential_check.py` (the app). Only `tests/engine/test_credential_testenv_parity.py` keeps them equal, and it runs only when the toolkit is found (the sibling clone); without it the test skips and the two can drift. Change both together.

## Dependency on a second repo
- The loop needs claude-dev-toolkit (skills and shared scripts). Without it the doctor FAILs and a bundle lacks the dev skills (listed as skipped by `doctor --access`); a contract change in the toolkit's shared scripts (`verify.py`, `regression_diff.py`, `testenv.py` output) is not caught by this repo's tests, which use a fake toolkit.
- Tests are hermetic on purpose: `tests/__init__.py` points `LOOP_CLAUDE_HOME` at an empty folder and hides the sibling clone (`../claude-dev-toolkit`) from `find_toolkit_root`; a test that forgets to set `dev_toolkit_dir` sees no toolkit instead of the developer's real one. Keep new tests behind that, or they will pass on one machine and fail on another.
- A `## Standards` binding is only checked by name: the doctor WARNs when the skill does not resolve, but the content of a bound skill is the company's and is never validated here.

## Containment is logical, not a sandbox
- A loop turn is held by its worktree, the `claude -p` flags (permission mode, push disabled through `GIT_CONFIG_*`) and the text rules of `plugin/skills/orchestrator/hooks/guard.py` (`loop-guard-hardening`: production SQL writes, credential files, HTTP uploads, agent allowlist and model ceiling, shell delete/copy/move targets, unreadable `SCOPE.json`, secret-looking variables of the app `.env` left out of the turn by `engine/turn_environment.py`). It runs as the user, with the user's network and files: anything the text analysis cannot see (a target in a variable, `python -c` opening a file, a symlink) stays possible.
- Isolation of the `claude -p` environment (`runtime_isolation.py`) removes the user's plugins, skills, hooks and plugin MCP servers from app sessions, and the guard's `mcp-allowlist` / `skill-allowlist` deny the rest by name. It is still the guard's text analysis, not a sandbox, and Claude Code's built-in skills stay visible (they cannot be hidden by a flag without losing `/orchestrator`; the guard denies them per profile). The bundle copies skills from `~/.claude/skills` when present, then from the toolkit, the Maestro plugin and the other installed plugins (the first with a `SKILL.md` wins), so an edited skill reaches the loop only after the bundle signature changes (names, mtimes, sizes) and the next `claude -p` rebuilds it.
- `--setting-sources project,local` also drops `~/.claude/CLAUDE.md` in app sessions (intended); the user's `autoMode` block is copied into the inline settings, the user's `permissions` are not.
- The one lock that does not depend on a regex is the database grant: the production MCP user should be SELECT-only in MySQL itself (the user's own setting, outside the repo).
- Next step when this is not enough: run each turn in a container or as a separate OS user with a network allowlist.

## Shell execution
- `app/backend/harness_backend/engine/worktrees.py` runs a repo's setup command with `shell=True`. The text must match the SHA-256 the user approved when typing it in the panel (`engine/setup_approval.py`, stored in the app data folder, outside the repos), and the guard forbids every profile from writing `REPOS.json`; existing projects re-save their setup once. The toolkit's `shared/verify.py` (outside this repo) still runs verify commands with `shell=True` from the spec, unvalidated.
