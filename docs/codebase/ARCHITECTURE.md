# Architecture

**Pattern:** two-part local tool. A **plugin** (the brain: prompts, agents, guard hook) and an **app** (the runtime: Python loop engine, local HTTP API, plain-JS panel). Everything runs on the user's machine and drives the `claude` CLI with the user's own subscription (no API token, no hosted service). Python 3.10+, standard library only; the front end has no build step.

For the full contract see `app/docs/ARCHITECTURE.md` (layers, modules, fixed signatures), `app/docs/API.md` and `app/docs/SKILL_BRIDGE.md`.

## High-Level Structure

```
repo root
  plugin/   Claude Code plugin: skills/ (orchestrator + satellites + repo-catalog), agents/, hooks/, shared/ (PROJECT_RULES.md, envload.py)
  app/      harness.py (single CLI) + backend/harness_backend + frontend + templates + docs
  install.py, .claude-plugin/marketplace.json   install entry points
```

The generic dev skills (`backend-dev`, `frontend-dev`, `tlc-spec-driven`, `flow-validator`, the Playwright skills) and their scripts live in a second plugin, **claude-dev-toolkit** (own repo, required by Maestro, never depending on it). `config/skill_locator.find_toolkit_root` finds it (`dev_toolkit_dir`, plugin cache, sibling clone); the orchestrator puts its path in a `TOOLKIT: <path>` line of every dispatch (`harness.py paths`). Company rules plug in through **standards slots** bound in the `## Standards` section of each project's (or subproject's) `CLAUDE.md` (`engine/standards.py`, `harness.py standards`); the bound skills join the isolation allowlists and bundle.

The skill finds the app through `LOOP_APP_HOME` or `~/.loop-harness/config.json` (written by `harness.py install`). The app finds the skill and its guard through `config/skill_locator.py`. Project state lives in the target repo under `.specs/` (roadmap, state, per-feature specs, `project/loop/` turn files); app state lives in `~/.loop-harness/` (`LOOP_DATA_DIR`).

## Identified Patterns

### Layered back end with constructor injection
**Location:** `app/backend/harness_backend/` (`api/controllers` -> `services` -> `repositories` -> `infrastructure`, plus `domain/`).
**Purpose:** keep HTTP, rules, file/git access and process access separate.
**Implementation:** abstractions are `typing.Protocol` named `I...`; concrete classes are built only in `composition.py` and each module's `build_*_module` function. Controllers expose `register_routes(router)`.
**Example:** `composition.py::build_application`, `services/projects_module.py`.

### Feature modules
**Location:** `services/*_module.py` (projects, loop read, loop commands, multi-repo).
**Purpose:** each module returns `controllers`, `busy_providers` (they prevent idle shutdown) and the services other modules consume.

### Engine as proven CLI scripts
**Location:** `backend/harness_backend/engine/` (e.g. `run_loop.py`, `loop_state.py`, `notify.py`, `delivery.py`, `close_loop.py`).
**Purpose:** the loop (roadmap -> spec -> gate -> exec -> verify) runs outside the HTTP process.
**Implementation:** services call engine scripts as subprocesses via `infrastructure/process_runner.py`, or import pure read functions (`loop_state.parse_roadmap`, `graph_view`). Engine scripts are standalone-runnable (path-insert imports, `app_paths`), unlike the layered code.
**`run_loop.py` after the split:** it stays the entry point (about 740 lines: `main`, `preflight`, `finish`, notices) and re-exports every name that moved to cohesive sibling modules, so `run_loop.<name>` keeps working for tests and services: `loop_io` (file, JSON, git, process helpers), `claude_accounts` (command and account fallback, usage windows), `limit_waits` (pause and limit waits), `claude_turn` (the `claude -p` argv, environment and run of a turn), `permission_denials`, `worktree_state` (what is read between turns, rewind, lock), `worktrees` (create and re-attach worktrees), `auto_answers`, `turn_gates` (checks between turns), `preflight_checks` and `loop_cli` (argparse). Functions that call something tests replace (`notify_wait`, `ensure_worktrees`, `planning_readiness`) stayed in `run_loop.py`.
**Example:** `services/engine_script_service.py`.

### Guarded agent sessions
**Location:** `plugin/skills/orchestrator/hooks/guard.py` (PreToolUse hook, profiles such as `auto` and `spec`), `plugin/hooks/hooks.json`, `infrastructure/workspace_file_guard.py`, `engine/runtime_isolation.py`, `engine/access_report.py`.
**Purpose:** agents cannot push, write outside their allowed folders, touch production or read secrets (every `.env` layer of the test environment included); delivery (push + PR) is only done by the orchestrator via `harness.py deliver`.
**Implementation:** with `LOOP_HEADLESS=1` (exported by the engine) every `git push` and `gh` is blocked for every caller and the main session without `agent_type` gets the `orchestrator` profile; an executor dispatched with `SCOPE_TASK: <slug>/<Tn>` is limited to that task's files (`SCOPE.json` `tasks`).
**Isolation and allowlists:** every `claude -p` the app starts (loop turns and panel jobs) runs with `--setting-sources project,local` plus `--add-dir=<data dir>/runtime/bundle`, a folder with only the 8 plugin agents and the allowlisted skills (`runtime_isolation.py`; kill switch `"loop_isolation": false` in `config.json`). The guard reaches the process through inline `--settings` (written to `runtime/settings-<hash>.json`), and the engine exports `LOOP_ISOLATED=1` and `LOOP_SKILLS_FILE` (the per-profile skills table). Two hard guard rules use them: `mcp-allowlist` (an `mcp__*` tool outside the profile's list is denied; DEV SQL for the querying profiles, PROD SQL only for `orchestrator` and `planning`, still read only through `sql-write` / `prod-sql-write`) and `skill-allowlist` (a `Skill` call outside the profile's list is denied, fail closed). Allowed MCP and Skill calls leave an `allow` line in `guard.log`. `harness.py doctor --access` reports it all and probes the real argv.

### Task waves
**Location:** `engine/task_waves.py` (also `harness.py tasks waves|set|mirror`), `repositories/task_status_repository.py`, `app/templates/specs/TASKS.md`.
**Purpose:** a feature with a `tasks.md` is built by one executor per task, in waves of at most `Max parallel tasks` (ROADMAP header, default 3); the status of each task is `loop/internal/tasks/<slug>.json`.

### Monorepo subprojects
**Location:** `engine/subprojects.py`, `services/subprojects_service.py`, `subproject_map_service.py`, `system_map_service.py`, `map_job_runner.py`, `engine/context_block.py`, `engine/system_map.py`.
**Purpose:** a repo with several projects gets a confirmed list (`.specs/project/SUBPROJECTS.json`), a Conformance and a map per subproject, and a root `docs/codebase/SYSTEM.md` for the contracts between them.
**Implementation:** every map job (root, subproject, system) goes through `MapJobRunner` (snapshot, `--model sonnet`, no spend cap, guard profile, revert of writes outside the allowed folders); subproject maps run as a persisted queue, all at once (up to `max_parallel_maps`, default 6): `ClaudeJobService` lets jobs with different `parallel_key` (subproject folder) run together and keeps every other job exclusive, and the system map starts by itself when every map is done. The setup is an installer card (Subprojects, Conformance, Maps; a single repo has Conformance, Map). A generated `maestro:context` block in each `CLAUDE.md` points the agents to the map. `SYSTEM.md` carries a "Who talks to whom" section (consumer -> provider, how, env name, routes). Executors never edit `SYSTEM.md`: features write `contract.md` and `run_loop` merges it between turns. Details in `app/docs/ARCHITECTURE.md` (Monorepos).

### Repositories, workspace and setup files
**Location:** `services/repo_registry_service.py`, `services/workspace_service.py`, `services/setup_commit_service.py`, `engine/setup_files.py`, `engine/project_repos.py`, `engine/run_loop.py`, `app/frontend/src/pages/panel/workspace_dialog.js`, `repo_setup_dialog.js`.
**Purpose:** a project lists its repositories with a role (edit or reference) and a reason written by the planning chat; each one is set up (Conformance, map) with the same installer, and the loop starts from the integration branch with the generated setup files carried in.
**Implementation:** no confirm step (the primary is always `edit`); `GET workspace` reports per repo the current branch, the base (`developer` when it exists locally, else the current branch), `base_sha`, upstream, setup state, `setup_files` and `other_changes`. A new worktree copies the uncommitted setup files it lacks (`carry_setup_files`, never over an existing file; `meta.json` records `base`, `base_sha`, `carried_setup_files`) and the pre-turn dirty check ignores them. **Commit setup files and push** (`SetupCommitService`) commits only those files on the current branch and pushes to its upstream (refuses `main`/`master`, detached HEAD, no upstream, running loop or job); the legacy `commit-push` route only acts on a loop worktree. Readiness shows one `uncommitted` block per edit repo. Details in `app/docs/ARCHITECTURE.md` (Multi-repo) and `app/docs/API.md`.

### Loop panel: settings in the plan, decisions as data, wrap-up as orchestration
**Location:** `domain/roadmap_settings.py`, `services/loop_control_service.py`, `engine/decisions.py`, `engine/run_loop.py`, `services/decisions_service.py`, `services/wrap_up_service.py`, `services/follow_up_service.py`, `app/frontend/src/pages/panel/` (navbar, dialogs).
**Purpose:** the loop panel is one navbar and two zones; what the user decides is decided before the run, and what the AI decided during it is reviewed afterwards.
**Implementation:** the nine run settings (dispatch, E2E, budgets, minutes, branch, setup, stuck policy, push and PR) are lines of the ROADMAP header parsed once by `parse_loop_settings`; the start body only carries `push` and `remove_worktree_on_finish` (stored in `meta.json` `delivery`). The orchestrator turn runs on `--orchestrator-model` (default Opus, `orchestrator_model` in `config.json`). The spend cap (default US$ 50, raisable per run through `meta.max_cost_usd`) PAUSES the loop (`paused`) instead of failing it. AI decisions are lines of `VALIDATE.md` with `turn=` and `level=`; a `critical` one stops the loop as `awaiting_user`; the review state is app-owned (`decisions-review.json`) and the file is never edited by the app. Finish (`WrapUpService`) only sequences the existing delivery and close pieces and refuses with a per-repo reason list (409 `wrap_up_blocked`); a follow-up (`FollowUpService`) is a Sonnet planning job that may only append one `Follow-up <n>` stage, then a normal round on the same worktree. Details in `app/docs/ARCHITECTURE.md` (Loop panel) and `app/docs/API.md`.

### Panel without build
**Location:** `app/frontend/` (`index.html`, `src/**/*.js`, `styles/*.css`, vendored Preact + htm in `vendor/`), served as native ES modules by `api/http_server.py`.

## Data Flow

### Loop turn
User clicks in the panel -> controller (`loop_commands_controller`) -> `LoopControlService` (options from the ROADMAP header settings) -> engine `run_loop.py` subprocess -> `claude -p --model <orchestrator model>` with the orchestrator skill (via `infrastructure/claude_client.py`) -> agents write `.specs/**` (decisions as lines of `VALIDATE.md`) -> after the turn the engine adds the turn cost to `meta.json`, pauses on the spend cap or on a new critical decision -> read services (`loop_status_service`, `loop_file_repository`) parse files -> panel polls `/p/<id>/api/...`.

### Finish and follow-up
Navbar Finish -> `workspace_controller` (`GET wrap-up`, `POST wrap-up/finish`) -> `WrapUpService` -> `delivery.py` (push + PR, when chosen) then `LoopWorktreeService.close_loop` -> `engine/close_loop.py` (verified backup, plan copied back, `last-run.json`, `git worktree remove`). Follow-up (a chat, thread per round in `loop/internal/follow-up/round-<n>.json`, US$ 1 per message and US$ 5 per round): `follow_up_controller` -> `FollowUpService` -> `claude_job_service` (type `follow_up`) -> the round's stage in the worktree ROADMAP -> `follow-up/run` (Continue loop) starts a round through `LoopControlService.start_new_loop`.

### Planning and roadmap (headless)
Panel chat/planning controller -> `planning_service.send_message` (cheap refusals, persist the user message, `start_job`, answer at once) -> in the job thread `before_start` (gates, snapshot, MCP access, isolation bundle, argv and prompt; a red gate ends the job as an error with `code: planning_prerequisites`) -> `claude -p` (isolated, read-only, scoped tools, MCP only the read servers the user has configured) -> `.specs` files written through `workspace_file_guard` limits. A spec import (`PlanningImportService`: preview, copy to `.specs/features/<slug>/`, `IMPORT-LOG.md`) makes the AI write `IMPORT-COVERAGE.md`; the `import_coverage` planning gate checks every source item against it. Folder pickers are native-first (`POST projects/pick-folder`).

### Delivery
`harness.py deliver` -> `engine/delivery.py`: push of the feature branch only, PR via `gh` or compare link (`LOOP_PR_MODE`).

## Code Organization

**Approach:** layer-based back end inside feature modules; the engine is a flat folder of scripts; the plugin is organized by kind (`skills/`, `agents/`, `hooks/`, `shared/`).

**Module boundaries:** hub API (`/api/app/...`, projects) vs per-project API (`/p/<id>/api/...`). Security stance: listens on 127.0.0.1 only, checks `Host`, requires a token on every mutating call, whitelisted actions with `confirm:true`, the orchestrator never calls trigger endpoints. See `api/http_server.py` and `app/docs/MONITOR.md`.

**Local-only extension:** `engine/local_ext/` (gitignored per its own docstring) is loaded by `notify.py` for private providers.
