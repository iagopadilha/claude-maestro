# Architecture

**Pattern:** two-part local tool. A **plugin** (the brain: prompts, agents, guard hook, shared scripts) and an **app** (the runtime: Python loop engine, local HTTP API, plain-JS panel). Everything runs on the user's machine and drives the `claude` CLI with the user's own subscription (no API token, no hosted service). Python 3.10+, standard library only; the front end has no build step.

For the full contract see `app/docs/ARCHITECTURE.md` (layers, modules, fixed signatures), `app/docs/API.md` and `app/docs/SKILL_BRIDGE.md`.

## High-Level Structure

```
repo root
  plugin/   Claude Code plugin: skills/ (orchestrator + dev skills), agents/, hooks/, shared/ (python helpers)
  app/      harness.py (single CLI) + backend/harness_backend + frontend + templates + docs
  install.py, .claude-plugin/marketplace.json   install entry points
```

The skill finds the app through `LOOP_APP_HOME` or `~/.loop-harness/config.json` (written by `harness.py install`). The app finds the skill and its guard through `config/skill_locator.py`. Project state lives in the target repo under `.specs/` (roadmap, state, per-feature specs, `project/loop/` turn files); app state lives in `~/.loop-harness/` (`LOOP_DATA_DIR`).

## Identified Patterns

### Layered back end with constructor injection
**Location:** `app/backend/harness_backend/` (`api/controllers` -> `services` -> `repositories` -> `infrastructure`, plus `domain/`).
**Purpose:** keep HTTP, rules, file/git access and process access separate.
**Implementation:** abstractions are `typing.Protocol` named `I...`; concrete classes are built only in `composition.py` and each module's `build_*_module` function. Controllers expose `register_routes(router)`.
**Example:** `composition.py::build_application`, `services/projects_module.py`.

### Feature modules
**Location:** `services/*_module.py` (projects, loop read, loop commands, multi-repo).
**Purpose:** each module returns `controllers`, `busy_providers` (they prevent idle shutdown) and the services other modules consume.

### Engine as proven CLI scripts
**Location:** `backend/harness_backend/engine/` (e.g. `run_loop.py`, `loop_state.py`, `notify.py`, `delivery.py`, `close_loop.py`).
**Purpose:** the loop (roadmap -> spec -> gate -> exec -> verify) runs outside the HTTP process.
**Implementation:** services call engine scripts as subprocesses via `infrastructure/process_runner.py`, or import pure read functions (`loop_state.parse_roadmap`, `graph_view`). Engine scripts are standalone-runnable (path-insert imports, `app_paths`), unlike the layered code.
**Example:** `services/engine_script_service.py`.

### Guarded agent sessions
**Location:** `plugin/skills/orchestrator/hooks/guard.py` (PreToolUse hook, profiles such as `auto` and `spec`), `plugin/hooks/hooks.json`, `infrastructure/workspace_file_guard.py`.
**Purpose:** agents cannot push, write outside their allowed folders, touch production or read secrets; delivery (push + PR) is only done by the orchestrator via `harness.py deliver`.

### Panel without build
**Location:** `app/frontend/` (`index.html`, `src/**/*.js`, `styles/*.css`, vendored Preact + htm in `vendor/`), served as native ES modules by `api/http_server.py`.

## Data Flow

### Loop turn
User clicks in the panel -> controller (`loop_commands_controller`) -> `LoopControlService` -> engine `run_loop.py` subprocess -> `claude -p` with the orchestrator skill (via `infrastructure/claude_client.py`) -> agents write `.specs/**` -> read services (`loop_status_service`, `loop_file_repository`) parse files -> panel polls `/p/<id>/api/...`.

### Planning and roadmap (headless)
Panel chat/planning controller -> `planning_service` / `claude_job_service` -> `claude -p` (read-only, scoped tools, empty MCP config unless opted in) -> `.specs` files written through `workspace_file_guard` limits.

### Delivery
`harness.py deliver` -> `engine/delivery.py`: push of the feature branch only, PR via `gh` or compare link (`LOOP_PR_MODE`).

## Code Organization

**Approach:** layer-based back end inside feature modules; the engine is a flat folder of scripts; the plugin is organized by kind (`skills/`, `agents/`, `hooks/`, `shared/`).

**Module boundaries:** hub API (`/api/app/...`, projects) vs per-project API (`/p/<id>/api/...`). Security stance: listens on 127.0.0.1 only, checks `Host`, requires a token on every mutating call, whitelisted actions with `confirm:true`, the orchestrator never calls trigger endpoints. See `api/http_server.py` and `app/docs/MONITOR.md`.

**Local-only extension:** `engine/local_ext/` (gitignored per its own docstring) is loaded by `notify.py` for private providers.
