# Headless mode: the orchestrator inside the unsupervised loop

Caller: `loop/run_loop.py` (Python script, outside Claude). Each round is a new conversation:

```
claude -p "/orchestrator continue --headless --turn N --wave W --branch B [--e2e]" --output-format json \
       --permission-mode auto --permission-prompts none --max-budget-usd <value>
```

The process ends on its own when the orchestrator gives its final reply. There is nobody to answer: **ending the round is the only way to "wait for the user"**.

## Arguments

| Argument | Means |
|---|---|
| `--headless` | no user. Do not ask, do not use `AskUserQuestion`, do not end the reply with a question. The checkpoint mode is `autopilot`. |
| `--turn N` | number of this round. Goes in `LOOP.json`. |
| `--wave W` | how many features per round (default 1). Only with `PATHS` disjoint from each other and from any `building` feature; otherwise reduce to 1 and record it in STATE. |
| `--branch B` | the loop branch. Check `git branch --show-current`; if it is another one, write `error` and stop. |
| `--e2e` | the user authorized the final flow-validation phase (Phase 6b), headless. |
| `--phase F` | the phase the **script** chose (`loop_state.py next`): `execute`, `gate`, `specs`, `recover` (lost dispatch, Phase 0), `final` (all verified/blocked: E2E or `done`) or `none` (nothing moves: write `awaiting_user` saying what blocks). Absent = decide as in `SKILL.md`. |
| (stage) | `next` only looks at the **current stage**: the first `## Stage N` of the ROADMAP with a still-open feature. Spec and execution of a future stage are not dispatched; the next stage only starts when this one closes (`verified`/`blocked`). |
| `--ready a,b` | the features the phase must dispatch: dependencies `verified`, `paths` disjoint from each other and from the `building` ones, at most `--wave`. **Dispatch exactly these**; do not swap or add. |
| `--stuck c` | features that depend on a `blocked` one. They do not move without the user: cite them in the `reason`. |

## What a round does

1. Normal Phase 0 (RULES, ROADMAP, STATE, only the previous phase). A mandatory stop detected here: write `awaiting_user` and stop.
2. The work comes from `--phase`/`--ready` (the script already applied the rule below with `loop_state.py next`; `deps=` and collision by `dir:` enter that calculation). Without those arguments, you choose the **most advanced work that exists**, and only it:
   - `approved` features -> execution wave (up to `--wave`): Phase 5, then Phase 6 one by one, then commit one by one;
   - else `specced` features that need a gate -> Phase 4 (gates in parallel, up to 3);
   - else `pending` features of the stage -> Phase 3 (specs in parallel, up to 3), then the gate for those that need it;
   - else, if everything is `verified`/`blocked`: final phase (below) or `done`.
   You may chain phases in the same round while it fits (spec -> gate -> execution of a wave), but **never start a wave without being able to finish its commit**.
3. Stage closing (`phases/stage-NN.md`, fixed sections in `state.md`) when the stage ends. The final summary file is generated by the script from them, so the headings must be exactly: `Delivered`, `User decisions`, `Lessons`, `Unverified`, `Blocked`, `For the next stage`.
4. **Last action: write `STATE.md` and then `.specs/project/LOOP.json`.** Always, even on failure.

## `LOOP.json` contract (only the orchestrator writes; the script reads)

**Write it with the command, not by hand:** `python ${CLAUDE_PLUGIN_ROOT}/skills/orchestrator/loop/loop_state.py loop <root> --status <continue|awaiting_user|done|error> --turn N --feature a,b --reason "..." --next "..." [--options "a|b"] [--to-check "x|y"]`. It validates the enum (an invented value such as `em_andamento` is rejected: exit 2) and stamps `at` with the real time. Live rehearsal: the model invented `status=em_andamento` and the round was lost.

```json
{"status": "continue|awaiting_user|done|error", "turn": 3, "feature": "slug1,slug2",
 "reason": "short text (the question, or the cause of the error)", "next": "what the next round does", "at": "2026-10-14T02:49:00"}
```

- `turn` must equal the `--turn` received. A different value = the script treats it as an error (stale LOOP.json).
- `continue`: there is work and nothing prevents it. `done`: everything `verified` or `blocked` and the final phase (if requested) is done. `awaiting_user`: mandatory stop or user decision; `reason` carries the questions **in batch**, numbered. `error`: something broke that is not the user's (environment build, worktree off the branch).
- Never write `done` with a feature in `building`/`speccing`.

## Guarantees the script checks after each round (typed state)
`run_loop.py` validates what you wrote with `loop/loop_state.py` and stops with `error` (pointing to `--rewind`) if: the ROADMAP leaves the grammar; there is an illegal transition; a feature becomes `verified` without a new commit; a feature disappears; `tries>=2` outside `blocked`; 2 `building` with overlapping `paths`; or `LOOP.json` breaks the schema. It also stores a state snapshot per round (`--rewind N` goes back in time) and stops if total spend passes `--max-cost`. To avoid surprises: run `python ${CLAUDE_PLUGIN_ROOT}/skills/orchestrator/loop/loop_state.py validate <root>` before writing `LOOP.json`, and, with `--wave` greater than 1, `... loop_state.py disjoint <root> slug1 slug2` **before** dispatching (exit 1 = reduce the wave). Full map and anti-loop ceilings: `references/graph.md`.

## User answers (`ANSWERS.md`) and notification
When the round ends in `awaiting_user`, the script notifies through the configured channels (console, toast, file, e-mail, webhook), and the notification carries the resume command with `--answer "..."`. The user runs that command and the script writes the answer to `.specs/project/ANSWERS.md` (blocks `## Answer <date> [pending]` with `Question:` and `User answer:`) and the loop continues.
- **Headless round Phase 0: read `ANSWERS.md` before anything else.** For each `[pending]` block: apply the decision (STATE.md; if it is a limiting rule, `RULES.md` citing the answer as the user's phrase, which `--answer` counts as explicit), and change the marker to `[applied]`. Only then choose the round's work.
- Optional `LOOP.json` fields that improve the notification: `options` (short list, e.g. `["yes","no"]`; becomes a ready command per option) and `to_check` (short list of what the user should check, e.g. `["the e-mail arrived with the correct subject"]`). Short text, no credentials and no file content.
- Who writes `ANSWERS.md`: the script (creates the block) and the orchestrator (changes `[pending]` to `[applied]`). Never a subagent (guard).
- **Default message (every channel, defined in `notify.py`):** normal text + a "How to continue" section with BOTH modes: (1) loop through the script, `--answer` command highlighted; (2) normal chat conversation with `/orchestrator`: does not run the script, answers in chat and the orchestrator operates normally. A notification coming from the normal chat (`--subject/--body`) carries only mode 2.
- The normal (interactive) orchestrator may also notify, when it stops in autopilot on a mandatory stop: `python ${CLAUDE_PLUGIN_ROOT}/skills/orchestrator/loop/notify.py --subject "..." --body-file <file>`. It only works if `${CLAUDE_PLUGIN_ROOT}/shared/.env` is configured (that is the authorization); the recipient is fixed in `.env`, never chosen by you.

## Mandatory stops in headless
All those of `SKILL.md` apply, plus: roadmap without approval (the script does not even start without `ROADMAP.md`, but check), missing `Conformance:`, only `blocked` features left, executor asked for a larger scope (`NEEDS_CONFIRM`), attempted write to PROD. In all: write `awaiting_user` with the reason and finish. **Do not try to work around it.**

## Quarantine without dirtying the tree
The script stops if the tree is dirty outside `.specs/`. A feature that went to `blocked` leaves a half-done edit in its `PATHS`: save it with `git stash push -u -m "quarentena-<slug>" -- <paths>` (non-destructive), record the stash name in STATE and move on. Never `git reset --hard`, `git clean` or `git checkout --`.

## Final phase (`--e2e`)
After all features are `verified` or `blocked`: dispatch the `verifier-flow` one feature at a time (serial; it uses ports), headless, with `FEATURE: <slug>`. Mark in the ROADMAP `e2e=ok|failed|not-covered` on the line of EACH `verified` feature (`not-covered` when there is no surface to test, e.g. a pure lib). **The script checks:** with `--e2e`, `done` without `e2e=` on some `verified` feature (or with `e2e=failed`) becomes `error`. `FAIL` -> the feature goes back to `approved` with `note=e2e-falhou` and the executor receives the `STEPS`; second failure -> `blocked`. Only write `done` when no feature is left with `e2e` pending. Without `--e2e` this phase does not exist and the build/lint/type `verifier` is what counts.

## Refactoring regression (`regression=` in the ROADMAP)
Independent of `--e2e`: the authorization is the field `regression=yes` approved in the ROADMAP (only `refactor-*` slugs). The feature moves **alone** in the wave (`next` already does that). In the round: baseline with `verifier-flow` (`MODE: baseline`) **before** the executor, regression (`MODE: new`) **after** the `verifier`. Baseline `UNVERIFIED` or a case that already fails on the old code = `awaiting_user` with the `RG-xx` in `--reason`. The old-code baseline is captured in the loop worktree before the feature's first edit, so it does not need a second copy of the repo. A Node project needs `--setup "npm ci"` (otherwise the app does not start and the baseline becomes `UNVERIFIED`). Details: `references/regression.md`.

## Git, push and PR (end of the flow)
The orchestrator commits on the loop branch (one commit per verified feature, with the configured git identity) and **never pushes** (the guard blocks it, and `claude -p` runs with the `pushurl` of every remote disabled via `GIT_CONFIG_*`, so not even a regex loophole pushes). The delivery at the end belongs to the **script**, only on `done`, **on by default** (`--no-push` turns it off): `loop/delivery.py` pushes **only the feature branch** (refuses `developer`/`develop`/`main`/`master`/`release`/`production`/`dev`, force and an open feature) and opens the **PR to `developer`** (`gh pr create`; reuses an already open PR; without `gh` or with `LOOP_PR_MODE=link`, only the compare link; `LOOP_PR_MODE=off` turns it off; `LOOP_PR_BASE` changes the base; `LOOP_PR_DRAFT=1` opens it as a draft). The PR link goes in the notification, in `meta.json` (`pr`, `pr_status`) and in the final summary. The PR body lists verified features, quarantines and `VALIDATE.md`.

## Loop satellites (`orchestrator-*` skills)
- **Block rule** (`loop/rules.py`): the preflight (`--check` and every start) runs `rules.py test`; a rule with a test that stopped passing is a `PROBLEM` (the loop does not start). A new rule is only created in a normal conversation, with the user's phrase (not in headless).
- **Dependencies** (`loop/audit_deps.py`): the preflight warns when there is a forgotten `deps=`. **Before each round `run_loop.py` itself runs `audit_deps.py --apply`** (it is the one that chooses `--ready` before claude runs; it only increases serialization) and the result is kept in `.specs/project/DEPENDENCIES.md`. The headless orchestrator does not need to run it.
- **Graph** (`loop/graph_view.py`): `run_loop.py` rewrites `.specs/project/GRAPH.md` every round and puts the drawing in the notification (text in the e-mail, a short line in short channels when it fits), in the summary and in the PR (Mermaid).

## Non-blocking vs blocking doubt
A one-off doubt (small, reversible divergence) **does not stop the round**: the orchestrator chooses the conservative path and writes a line in `.specs/project/VALIDATE.md` (`- [slug] doubt | escolhi: ... |doubt \| chose: ... \| revert: ...`). Only a blocking question (architecture, scope, data, irreversible, PROD, spec vs rule) becomes `awaiting_user`. `VALIDATE.md` appears in the summary, in the completion notification and in the PR. Quarantine (`blocked`) only pauses the loop when another feature depends on the blocked one (`--pause-on-blocked` always pauses; `--continue-on-blocked` never). The worktree `../<project>-worktree-loop` belongs to the script: never create, delete or switch worktree on your own in headless (the manual worktree protocol of `dispatch.md` only applies in interactive mode).

## When testing
`python ${CLAUDE_PLUGIN_ROOT}/skills/orchestrator/loop/run_loop.py <repo> --dry-run` shows what it would do without executing anything. `loop_summary.py <folder>` generates the summary at any time, without Claude.
