# Planning mode: `/orchestrator plan [--headless]`

A conversation that **writes** the plan. Each user message is one turn: read it, update the planning documents, reply in plain language and stop. The app's planning screen (a project with no approved roadmap that never ran a loop) calls it with `--headless` in one `claude -p` session resumed on every message; in a chat it works the same way, one turn per message. The first prompt is `/orchestrator plan --headless` followed by the user's message; every later message of the resumed session is a new turn of this same mode, with the same limits.

## What it may touch

- **Writes only** `.specs/project/PROJECT.md`, `.specs/project/RULES.md`, `.specs/project/ROADMAP.md`, `.specs/project/FLOWS.md` and `.specs/project/TEST-ENVIRONMENT.md` (a short file: a 2 to 3 line summary plus small TABLES of variable NAMES, no prose sections; template in the app's `templates/TEST_ENVIRONMENT.md`; **never write a value**: the user puts values in `.specs/project/.env.test` or `~/.loop-harness/.env`; DEV only, never production). Every one of these files is born ready from the app's templates (RULES, STATE, an empty ROADMAP, FLOWS, PROJECT, TEST-ENVIRONMENT.md and `.env.test`): you fill them, you do not create the structure. Nothing else: not `CLAUDE.md`, `STATE.md`, `.specs/features/`, the loop folder or code.
- **Reads** `.specs/project/REPOS.json` when it exists (the repo names and each `role`, missing = `edit`), the index of the repo catalog when it is multi-repo (below), those three, `docs/codebase/*.md` (legacy: `.specs/codebase/`) when it exists, read on demand and never as the source of truth, and the code only through `Grep`/`Glob`/`Read` to settle one concrete point (where a module lives, which route already exists). Never a full exploration: mapping is `/orchestrator map` (or the panel's Map button).
- **Never:** Bash or PowerShell, subagents (`Agent`, `Plan`, mappers), MCP tools, loading other skills, resolving `<app>`, opening the panel, git, approving the roadmap (`ROADMAP-APPROVED.json` and `/p/<id>/api/roadmap/approve` are the user's click), starting or checking a loop. "Approved" in the chat is not approval: answer that the **Approve roadmap** button does it.
- **Fast turn.** A turn costs little (the app caps it at US$ 2 and 10 minutes): read only what the message needs, edit with `Edit` (a `Write` only to replace an untouched template), reply and finish.

**Prerequisites are not this mode's job:** git repo, `.specs/` structure, `Conformance:` in `CLAUDE.md` and, when the repo has code, the `docs/codebase/` map (or the legacy `.specs/codebase/`). The app refuses the message without them. In a chat, if one is missing, say which in one line (structure and Conformance: the panel's buttons or the normal `/orchestrator`; map: `/orchestrator map`) and stop.

## One turn

0. **The app sends a `[Planning status from the app]` block before every message**: each gate of the checklist as `OK`, `MISSING` or `optional`, with the reason and the items (for example which features have no flow in FLOWS.md, or `FLOWS.md missing`). It is the source of truth for what exists and what is missing: work on the `MISSING` lines first and never ask the user for something marked `OK`. A missing document is not a reason to wait: write it (the first draft rule below).
1. **Read** the message, then the planning files, every turn: the user may have edited them, and the file beats your memory of it. On the first turn also skim `STACK`, `ARCHITECTURE` and `STRUCTURE` of `docs/codebase/` (or the legacy `.specs/codebase/`) if they exist, once; later turns read a codebase doc only when the message needs it, never all seven. Stack, framework, language, database, dependencies, goals with a metric and scope are **never asked of the user**: they come from `docs/codebase/` or from the code. Ask only what the vision line, the features, the flows and the limits still lack.
2. **Apply** the message:
   - a goal or a request (first message, "add X", "split Y", "drop stage 3") = change the documents now. The first turn writes a full first draft of all three from the goal; do not wait for answers to draft.
   - an answer = put the decision where it belongs (the vision line, a `RULES.md` row, a feature line, a stage, a flow step) and **delete that question** from `## Open questions`.
   - a doubt about the plan = answer it; change nothing unless it asks.
3. **Keep the files consistent** (rules below), then **reply**.

## The documents

- **PROJECT.md** (the loop's short context file for subagents, about 300 words; it is born ready from the template): the `**Vision:**` line (1-2 sentences: what is being built and for whom) is the only `FILL_IN`; fill it, and a `FILL_IN` left keeps the gate "Project context" red. The `## Where to look` pointers are static: leave them. It holds no stack, goals, scope or constraints: the stack and conventions live in `docs/codebase/`, the limits in `RULES.md`, the features in the ROADMAP.
- **RULES.md** (born ready, empty): what the user says cannot be done (environment limits such as a port, database or service that cannot be touched; architecture limits such as a layer rule, a folder that gets no new code or a forbidden lib; what is permanently out of scope) becomes one row each (`ID`, `Rule`, `Why`, `How to apply`, `Origin` = the user's phrase and date), never a line in PROJECT.md. After approval a row that a command or path can block can also become a block rule (`orchestrator-create-block-rule`).
- **ROADMAP.md**: format of `references/state.md`. `**Goal:**` filled; stages `## Stage N — Name` with a **Name that says the outcome of the stage** (`## Stage 1 — Customers can register`, never `## Stage 1 — Stage 1` or `— Backend`); one line per feature `- [slug] status=pending title="..." ...`, **slug in kebab case, unique, 3 to 6 meaningful words naming what the feature delivers** (`customer-registration-api`; never an abbreviation, a number or a generic word such as `feat-2`, `misc`, `cfg`) and **`title` a short sentence of what the user gets** (`title="Register a customer with a tax id"`, double quotes, no inner quote, at most ~80 characters). A feature you rename is renamed everywhere (ROADMAP, FLOWS.md) before the user approves. `scope`, `kind` and `paths` may stay empty (the `spec-writer` fills them); fill `kind`/`paths` only when the map makes them obvious, and design for the wave (disjoint `paths`, `deps=` for what must be verified first, `dir:` for a folder only imported; `references/dispatch.md`). Without a validator in this mode, check by eye: every `status=pending`, enum values only, every `deps=` slug exists, no cycle. `regression=yes` only when the user asks for it (`references/regression.md`).
- **Which repo each path belongs to (only when `REPOS.json` lists more than one repository; never asked in a single-repo project).** Before you write a `paths=` entry for a feature, decide the repo of each path. Read `~/.loop-harness/repo-catalog.json`, using only each repo's `name`, `purpose` and capability `id`s (never open the repo folders or the capability descriptions). Propose the repo that already does what the feature needs, citing the capability id, and say so when the catalog has no match or the entry is `weak` or stale. Ask the user to confirm (one of the 1 to 3 questions: `a) <repo> (recommended) b) <other>`). Write `paths=<repo>:<path>` (and `repo-order=` when one repo must be built before another) only after the user confirms; until then leave `paths=` empty and keep the question in `## Open questions`. The primary repo needs no prefix. A repo that is not yet in `REPOS.json` goes first into `REPOS-SUGGESTED.json` (next bullet): once the server applied it (the status block shows it) you may use it in `paths=`; a `reference` repo never appears in `paths=` (nothing is written there).
- **Repositories from the chat or from an imported spec (REPOS-SUGGESTED.json).** When the user says which repositories to change or read (in the chat, or in a spec imported from a folder), write `.specs/project/REPOS-SUGGESTED.json`: `{"repos": [{"path": "<absolute folder>", "role": "edit|reference", "reason": "<one sentence>"}]}`, at most 10 entries, the whole file replaced each time. The planning chat manages the project's repositories; there is no "confirm these repositories" step: you add or change them and tell the user. Whenever you add a repository or change a role, write its `reason` (one sentence: why it is in the project and why this role) and say in plain words what the role means: **edits** = the loop changes it (own worktree on a new `loop/*` branch from the integration branch `developer`, PR to `developer` at the end); **reference** = read only, the agents may read it for contracts and examples, it is never changed and has no worktree. (`role` in the file stays `edit` or `reference`.) The server validates and applies it to `REPOS.json` right after your reply (you never edit `REPOS.json`); a path it refuses (not a git folder, not found, outside the allowed folders) comes back in the next `[Planning status from the app]` block with the reason: fix the path or ask the user, do not repeat it. Resolve each name to a folder in this order: (1) the repo catalog (`~/.loop-harness/repo-catalog.json`: `name`, `purpose` and capability `id`s only; never open the catalog repo folders to decide), (2) a search of the local folders (the project's parent folder and the folders the user names), (3) ask the user. The primary repository is always `edit`: do not list it. Every entry needs a `reason` (why the repo is in the project and why this role). A newly added repository goes through the app's setup installer (monorepo? -> subprojects -> Conformance -> maps); for a `reference` repository the map is optional but recommended and there is no Conformance. Setup files not yet committed (maps, `CLAUDE.md` app blocks, `.specs` plan files) are carried into the worktree by the Start, or the user can commit them from the Workspace dialog (Commit setup files and push on the current branch). Never guess a path, never invent a catalog name; write `{"repos": []}` when nothing is suggested anymore.
- **Importing a spec.** The app copies a **spec feature** the user brings (a tlc-spec-driven feature folder: `spec.md` required, plus `design.md`, `tasks.md`, `context.md` when present; a single file or pasted text is never imported) to `.specs/project/loop/internal/planning/imported/<stamp>-<name>/` and sends one message that names those paths. Read the files with `Read` (they are copies with secret values redacted: never ask for them back), then in the same turn: (1) write the **ROADMAP**: stages and one line per feature with a descriptive slug (3 to 6 words, kebab case, one per deliverable or per track/task group of the spec, never `task-1`), `title="..."` (what the user gets), `paths=<repo>:<path>` taken from the files the spec lists (a repo prefix for every repo other than the primary), `deps=` from the order the spec gives (a task that needs another's output depends on it) and `repo-order=` when one repo must be built first; (2) write **FLOWS.md**, one flow per feature from the spec's acceptance criteria and user stories; (3) fill the **PROJECT.md** vision line from the spec's goal; (4) put every ambiguity or missing decision in `## Open questions` with a recommended option; (5) write `REPOS-SUGGESTED.json` for the repositories the spec names (rule above). Do not paste the spec text into the plan and do not edit the imported files.
- **The capabilities block of PROJECT.md is not yours.** Between `<!-- maestro:capabilities -->` and `<!-- /maestro:capabilities -->` (section "What the agents can use") the app writes the real access: MCP servers with their read tools, credential names, test commands and each repository's role. It is rewritten after every reply, repo change and approval; **never edit inside the markers** (the guard reverts your edit to that file). Read it to know what exists before you promise a test or a data sample; edit PROJECT.md only outside the markers.
- **Monorepo (only when `SUBPROJECTS.json` is confirmed; the status block lists the subprojects).** `paths=` start with the subproject folder (`backend/...`, `frontend/...`). A front-end feature `deps=` the back-end feature that changes its API. **Giant files (GIANT-01):** the status block lists giant files per subproject. For each feature whose `paths` touch one, add an `## Open questions` line proposing a feature `refactor-<descriptive-slug>` that splits it, `| recommended: yes, with regression=yes, in an earlier stage and in this feature's deps=`; split by the subproject's Conformance (STANDARD: the dev skill's layers; LEGACY: a minimal split by responsibility inside the same layer). Never add it silently. If the user answers "not now", write `note=giant-accepted` on the touching feature.
- **`## Open questions`** (in the ROADMAP): every doubt not yet answered, one per line, `- <question> | recommended: <option>`; nothing else in the section (no prose, no comment). Empty = the single line `- none`. Approval needs it empty.
- **Regression proof (ask at most once, only when the ROADMAP has refactoring features):** tell the user it exists: the loop captures how a flow behaves before the change and compares after. It is requested per feature with `regression=yes`, ONLY on slugs starting with `refactor-` (the validator rejects it elsewhere; a slug like `refat-*` does not count: point that out and propose the rename `refactor-*` when the user wants regression). Ask: "Do you want regression proof on these? It needs flows and a test user." It requires (a) a flow for that feature in FLOWS.md and (b) test variables: credential NAMES in `.specs/project/TEST-ENVIRONMENT.md`, VALUES in `.specs/project/.env.test` (this project) or, when the project does not define them, the machine defaults in `~/.loop-harness/.env` (the standard test user, `TEST_USER_1_*`). If it cannot run, the loop does not start and an e-mail/notice says what is missing. Put `regression=yes` only after the user says yes; if they decline or do not answer, leave it off and do not ask again.
- **E2E (project-wide, ask at most once):** the ROADMAP header carries one line under `**Goal:**`: `**E2E:** yes|no` (default `no`). Meaning, in one line to the user: "at the end the loop runs every flow of FLOWS.md against the real app (routes and screens) and records e2e=ok|failed|not-covered per feature; it needs a filled-in TEST-ENVIRONMENT.md and test user". It is decided HERE, in planning: the start step only shows it, read-only (an old client that still sends `e2e` explicitly wins; otherwise the loop reads this line from the approved ROADMAP). Ask once ("Do you want the final end-to-end validation of the flows? yes/no"), write `**E2E:** yes` only after the user says yes; if they decline or do not answer, keep `**E2E:** no` and do not ask again. With `yes`, say that the "Test environment" tab must be filled in (the loop refuses to start without it).
- **Loop settings (ask or propose them in the conversation; they live in the ROADMAP header, under `**Goal:**`, one `**Name:** value` line each).** Planning is where they are decided: the loop reads them from the approved ROADMAP and nothing else sets a limit (the panel's start step only shows them, read-only). Names exactly: `**E2E:**` (yes|no, default no; see above), `**Dispatch:**` (auto or a number of lanes per turn, default auto), `**Max spend per turn:**` (US$, default 5), `**Max spend for the loop:**` (US$, default 50), `**Max minutes per turn:**` (default 60), `**Branch:**` (empty = automatic), `**Branch base:**` (the integration branch: new worktrees start from it and the delivery PR targets it; default `developer`; propose it and ask the user to confirm which branch the team integrates into; the loop falls back to the current branch with a warning when it does not exist locally), `**Setup:**` (the install command, e.g. `npm ci`; empty = none), `**When a feature gets stuck:**` (pause|continue, default pause), `**Push and PR:**` (yes|no, default yes). On the first draft write every line with its default, propose the ones the project clearly needs (a Node project: `Setup`; a big roadmap: a higher loop spend), and ask the user in one question only about the ones that change cost or risk (spend caps, stuck behaviour, push). A value the app cannot parse is reported as a problem on that header name: fix the line, do not leave it. Never put a secret in a setting.
- **FLOWS.md**: one `## [slug] Title` section per ROADMAP feature, with the same slug and the same title as its ROADMAP line, at least 2 numbered steps and `Expected:` lines that can be observed (status, field, visible text, a row in the database). Format and parse rule in `references/state.md`. A renamed or removed feature renames or removes its section. A feature with no screen and no route (model, migration, job) still gets a flow: what you run and what you then observe.

- **TEST-ENVIRONMENT.md** (gate `test_environment` of the status block, shown to the user as the "Test environment" tab): how the loop will run and test the real app. The app creates the file from its template before your first turn, so you `Edit` it. It never blocks the approval, but a feature with `regression=yes`, or the user wanting `--e2e`, makes the loop refuse to start without it, so when the status block shows it `MISSING`/`optional` and the ROADMAP asks for regression, say so in the reply. Keep it DIRECT, like the other tabs: a 2 to 3 line summary of what is tested, then only the template's four small tables: where it runs (item, variable, note: `$LOCAL_URL`), login to get the access token (user variable, password variable, how the token is obtained: `$TEST_USER_1_EMAIL` / `$TEST_USER_1_PASSWORD`; the generic DEV account of the shared fallback covers a project that defines none), API headers and tokens (header or call, variable name, where to get it: while analyzing the routes' code record the SOURCE of each header/token/secret, in this order: `appsettings: <file>:<Key:Path>` when the key exists in appsettings*.json or the repo's config/.env.example, `Infisical: <key> (<path/environment>)` when the code reads it from the secret manager (exact key name as visible in code or config), otherwise `FILL_IN`; names and keys only, never open Infisical or a real `.env` and never write a value), and test data (what, variable: only the `$SAMPLE_*` names a feature uses, taken from FLOWS.md). No explanatory sections (what it is for, what may be tested, what must never be done: obvious). Add a row or a table only when something needs it. **Never a value**, never a password in the chat or the file. When you do not know a fact, ask the user (one of the 1 to 3 questions) instead of writing a guess; a `FILL_IN` left keeps the gate not ready. Put `$` only on names that exist (the preflight flags any `$NAME` no `.env` defines, even in a comment). Tell the user the VALUES go in `.specs/project/.env.test` (this project) or `~/.loop-harness/.env` (this machine), both ignored by git. When `.specs/project/ACCESS.json` says `{"grafana_read": true}` (absent or false means not allowed), when this turn has those tools you may use the `idata-grafana` skill and the read-only Grafana MCP tools to fetch ONE sample of each `$SAMPLE_*` the features need; show the sample values to the user in the chat and never write them into any file (the app writes `.env.test` on the user's click).

## The reply

Short, plain language, no file dumps:

```
Changed: PROJECT vision; RULES 2 rows; ROADMAP 2 stages, 5 features; FLOWS one flow per feature.
Still missing for approval: 3 open questions.

1. Can a customer register without a tax id? a) no, required (recommended) b) yes, optional
2. Is the admin screen in v1? a) no, stage 2 (recommended) b) yes
```

- `Changed:` what changed in each file you touched, in one line, or `Nothing changed.`
- `Still missing for approval:` only what is still red among goal, features, open questions and flows (the app shows the full checklist). Omit the line when nothing is missing, and say instead that the roadmap is ready for the **Approve roadmap** click.
- Then the **1 to 3 most important questions** (the ones that change stages, features or scope the most), numbered, with options and the recommended one. Asked or not, every doubt stays in `## Open questions` until answered; the reply only picks the top ones. Asking here is the point of this mode: unlike `roadmap --headless`, it ends with questions.
