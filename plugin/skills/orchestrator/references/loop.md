# Headless mode: the orchestrator inside the unsupervised loop

Caller: the Loop Harness engine (`python "<app>/harness.py" loop <repo>`, script `run_loop.py`, Python outside Claude; `<app>` resolved as in `SKILL.md`, section Runtime). Each turn is a new conversation:

```
claude -p "/orchestrator continue --headless --turn N --wave W --branch B [--e2e]" --output-format stream-json --verbose \
       --permission-mode auto --permission-prompts none --max-budget-usd <value>
```

The process ends on its own when the orchestrator gives its final reply. There is nobody to answer: **ending the turn is the only way to "wait for the user"**.

## Arguments

| Argument | Means |
|---|---|
| `--headless` | no user. Do not ask, do not use `AskUserQuestion`, do not end the reply with a question. The checkpoint mode is `autopilot`. |
| `--turn N` | number of this turn. Goes in `LOOP.json`. |
| `--wave W` | how many features (lanes) move in parallel per turn (default 3, `Dispatch` in the ROADMAP header), each with its own agent at every step. Executions only with `PATHS` disjoint from each other and from any `building` feature; otherwise that feature waits (stays `approved`) and the others carry on. |
| `--branch B` | the loop branch. Check `git branch --show-current`; if it is another one, write `error` and stop. |
| `--e2e` | the user authorized the final flow-validation phase (Phase 6b), headless. |
| `--lanes a:spec,b:gate,c:execute` | the lanes the **engine** chose (`loop_state.py next`): one per feature, each at ITS OWN step: `spec` (spec-writer), `gate` (spec-reviewer), `execute` (executor, then verifier), `recover` (lost dispatch of a `building`/`speccing` feature, Phase 0). Start each lane at that step and advance it by itself (`SKILL.md`, "Lanes"). |
| `--phase F` | summary of the lanes: the step they all share (`execute`, `gate`, `specs`, `recover`), `lanes` (they differ), `final` (all verified/blocked: E2E or `done`) or `none` (nothing moves: write `awaiting_user` saying what blocks). Absent = decide as in `SKILL.md`. |
| (stage) | `next` only looks at the **current stage**: the first `## Stage N` of the ROADMAP with a still-open feature. Spec and execution of a future stage are not dispatched; the next stage only starts when this one closes (`verified`/`blocked`). |
| `--ready a,b` | the slugs of the lanes (same as in `--lanes`): the `execute` ones have dependencies `verified` and `paths` disjoint from each other and from the `building` ones; at most `--wave`. **Start exactly these**; do not swap or add. |
| `--stuck c` | features that depend on a `blocked` one. They do not move without the user: cite them in the `reason`. |

## What a turn does

1. Normal Phase 0 (RULES, ROADMAP, STATE, only the previous phase, `ANSWERS.md`). A mandatory stop detected here: write `awaiting_user` and stop.
2. The work comes from `--lanes` (the engine already applied the rule below with `loop_state.py next`; `deps=` and collision by `dir:` enter that calculation). **Each lane is one feature with its own agents** (`SKILL.md`, "Lanes"): dispatch rounds of one agent per live lane, each at its own step, and move every lane on as soon as ITS step passed (spec -> gate -> execute -> verify -> commit), committing each feature when it is verified, without waiting for the other lanes. A failed or quarantined lane only holds its dependents. Without `--lanes`, you choose the lanes yourself, by the same priority (most advanced first):
   - `approved` features (deps verified, disjoint `paths`) -> execution lanes (up to `--wave`);
   - `specced` features that need a gate -> gate lanes;
   - `pending` features of the stage -> spec lanes;
   - if everything is `verified`/`blocked`: final phase (below) or `done`.
   A lane keeps going through its next steps in the same turn while the turn has room, but **never start an executor without being able to verify and commit it**.
   Inside an execution lane the build runs in task waves (`SKILL.md`, "Build phase per task wave"): `harness.py tasks waves <slug>`, one executor per task, at most `Max parallel tasks` per wave, the total across lanes inside `Max spend per turn` and `Max minutes per turn` (shrink the wave when short); one `verifier` after the last wave, `tasks mirror` and one commit. A turn cut off mid-feature resumes at the first not-done task (`tasks waves` lists only those). Headless: you only commit; you never push and never call gh; delivery belongs to the engine.
3. Stage closing (`phases/stage-NN.md`, fixed sections in `state.md`) when the stage ends. The final summary file is generated by the engine from them, so the headings must be exactly: `Delivered`, `User decisions`, `Lessons`, `Unverified`, `Blocked`, `For the next stage`.
4. **Last action: write `STATE.md` and then `.specs/project/loop/json/LOOP.json`.** Always, even on failure.

## `LOOP.json` contract (only the orchestrator writes; the engine reads)

**Write it with the command, not by hand:** `python "<app>/harness.py" state loop <root> --status <continue|awaiting_user|done|error> --turn N --feature a,b --reason "..." --next "..." [--options "a|b"] [--to-check "x|y"]`. It validates the enum (an invented value such as `in_progress` is rejected: exit 2) and stamps `at` with the real time. Live rehearsal: the model invented a status value and the turn was lost.

```json
{"status": "continue|awaiting_user|done|error", "turn": 3, "feature": "slug1,slug2",
 "reason": "short text (the question, or the cause of the error)", "next": "what the next turn does", "at": "2026-10-14T02:49:00"}
```

- `turn` must equal the `--turn` received. A different value = the engine treats it as an error (stale LOOP.json).
- `continue`: there is work and nothing prevents it. `done`: everything `verified` or `blocked` and the final phase (if requested) is done. `awaiting_user`: mandatory stop or user decision; `reason` carries the questions **in batch**, numbered. `error`: something broke that is not the user's (environment build, worktree off the branch).
- Never write `done` with a feature in `building`/`speccing`.

## Guarantees the engine checks after each turn (typed state)
`run_loop.py` validates what you wrote with the engine's `loop_state.py` and stops with `error` (pointing to `--rewind`) if: the ROADMAP leaves the grammar; there is an illegal transition; a feature becomes `verified` without a new commit; a feature disappears; `tries>=2` outside `blocked`; 2 `building` with overlapping `paths`; or `LOOP.json` breaks the schema. It also stores a state snapshot per turn (`--rewind N` goes back in time) and stops if total spend passes `--max-cost`. To avoid surprises: run `python "<app>/harness.py" state validate <root>` before writing `LOOP.json`, and, with `--wave` greater than 1, `python "<app>/harness.py" state disjoint <root> slug1 slug2` **before** dispatching (exit 1 = reduce the wave). Full map and anti-loop ceilings: `references/graph.md`.

## User answers (`ANSWERS.md`) and notification
When the turn ends in `awaiting_user`, the engine notifies through the configured channels (console, toast, file, e-mail, webhook), and the notification carries the resume command with `--answer "..."` and the panel link. The user answers (that command, or the panel) and the engine writes the answer to `.specs/project/loop/ANSWERS.md` (blocks `## Answer <date> [pending]` with `Question:` and `User answer:`) and the loop continues.
- **Headless turn Phase 0: read `ANSWERS.md` before anything else.** For each `[pending]` block: apply the decision (STATE.md; if it is a limiting rule, `RULES.md` citing the answer as the user's phrase, which `--answer` counts as explicit), and change the marker to `[applied]`. Only then choose the turn's work. A block with `Question: (user instruction from the panel)` or `(user note from the panel)` is handled the same way (see `SKILL.md`, Headless mode).
- Optional `LOOP.json` fields that improve the notification: `options` (short list, e.g. `["yes","no"]`; becomes a ready command per option) and `to_check` (short list of what the user should check, e.g. `["the e-mail arrived with the correct subject"]`). Short text, no credentials and no file content. Write the options in English and mark the conservative one `(recommended)`: the automatic answer below reads that word.
- Who writes `ANSWERS.md`: the engine and the panel (create the block) and the orchestrator (changes `[pending]` to `[applied]`). Never a subagent (guard).
- **Default message (every channel, defined in the engine's `notify.py`):** normal text + a "How to continue" section with every mode: (1) the loop command, `--answer` highlighted; (2) the panel link ("answer in the panel"); (3) normal chat conversation with `/orchestrator`: does not run the loop, answers in chat and the orchestrator operates normally. A notification coming from the normal chat (`--subject/--body`) carries only the chat mode.
- The normal (interactive) orchestrator may also notify, when it stops in autopilot on a mandatory stop: `python "<app>/harness.py" notify --subject "..." --body-file <file>`. It only works if the app's `.env` (`~/.loop-harness/.env` or `${CLAUDE_PLUGIN_ROOT}/shared/.env`) is configured (that is the authorization); the recipient is fixed in `.env`, never chosen by you.

## Mandatory stops in headless
All those of `SKILL.md` apply, plus: roadmap without approval (the engine's preflight refuses a roadmap without `ROADMAP-APPROVED.json` matching its signature, but check), missing `Conformance:`, executor asked for a larger scope (`NEEDS_CONFIRM`), attempted write to PROD. In all: write `awaiting_user` with the reason and finish. **Do not try to work around it.** Only `blocked` features left is **not** a stop: finish `done` (see `SKILL.md`, "Headless: quarantine and small decisions do NOT ask").

## Quarantine without dirtying the tree
The engine stops if the tree is dirty outside `.specs/`. A feature that went to `blocked` leaves a half-done edit in its `PATHS`: save it with `git stash push -u -m "quarantine-<slug>" -- <paths>` (non-destructive), record the stash name in STATE and move on. Never `git reset --hard`, `git clean` or `git checkout --`.

## Final phase (`--e2e`)
After all features are `verified` or `blocked`: dispatch the `verifier-flow` one feature at a time (serial; it uses ports), headless, with `FEATURE: <slug>`. Mark in the ROADMAP `e2e=ok|failed|not-covered` on the line of EACH `verified` feature (`not-covered` when there is no surface to test, e.g. a pure lib). **The engine checks:** with `--e2e`, `done` without `e2e=` on some `verified` feature (or with `e2e=failed`) becomes `error`. `FAIL` -> the feature goes back to `approved` with `note=e2e-failed` and the executor receives the `STEPS`; second failure -> `blocked`. Only write `done` when no feature is left with `e2e` pending. Without `--e2e` this phase does not exist and the build/lint/type `verifier` is what counts.

## Refactoring regression (`regression=` in the ROADMAP)
Independent of `--e2e`: the authorization is the field `regression=yes` approved in the ROADMAP (only `refactor-*` slugs). The feature moves **alone** in the wave (`next` already does that). In the turn: baseline with `verifier-flow` (`MODE: baseline`) **before** the executor, regression (`MODE: new`) **after** the `verifier`. A baseline entirely `UNVERIFIED` or a case that already fails on the old code = `awaiting_user` with the `RG-xx` in `--reason`; a partial gap becomes `not-covered` and the feature continues. The old-code baseline is captured in the loop worktree before the feature's first edit, so it does not need a second copy of the repo. A Node project needs `--setup "npm ci"` (otherwise the app does not start and the baseline becomes `UNVERIFIED`). The preflight refuses to start without `.specs/project/TEST-ENVIRONMENT.md` filled in (no `FILL_IN`). Details: `references/regression.md`.

## Git, push and PR (end of the flow)
The orchestrator commits on the loop branch (one commit per verified feature, with the configured git identity) and **never pushes** (the guard blocks it, and `claude -p` runs with the `pushurl` of every remote disabled via `GIT_CONFIG_*`, so not even a regex loophole pushes). The delivery at the end belongs to the **engine**, only on `done`, **on by default** (`--no-push` turns it off): `harness.py deliver` (the engine's `delivery.py`) pushes **only the feature branch** (refuses `developer`/`develop`/`main`/`master`/`release`/`production`/`dev` and the integration branch, force and an open feature) and opens the **PR to the integration branch** (`LOOP_INTEGRATION_BRANCH`, default `developer`; `gh pr create`; reuses an already open PR; without `gh` or with `LOOP_PR_MODE=link`, only the compare link; `LOOP_PR_MODE=off` turns it off; `LOOP_PR_BASE` changes the base; `LOOP_PR_DRAFT=1` opens it as a draft). The PR link goes in the notification, in `meta.json` (`pr`, `pr_status`) and in the final summary. The PR body lists verified features, quarantines and `VALIDATE.md`.

## Loop satellites (`orchestrator-*` skills)
- **Block rule** (`harness.py rules`): the preflight (`--check` and every start) runs `rules.py test`; a rule with a test that stopped passing is a `PROBLEM` (the loop does not start). A new rule is only created in a normal conversation, with the user's phrase (not in headless).
- **Dependencies** (`harness.py audit`): the preflight warns when there is a forgotten `deps=`. **Before each turn `run_loop.py` itself runs `audit_deps.py --apply`** (it is the one that chooses `--ready` before claude runs; it only increases serialization) and the result is kept in `.specs/project/loop/DEPENDENCIES.md`. The headless orchestrator does not need to run it.
- **Graph** (`harness.py graph`): `run_loop.py` rewrites `.specs/project/loop/GRAPH.md` every turn and puts the drawing in the notification (text in the e-mail, a short line in short channels when it fits), in the summary and in the PR (Mermaid). The panel shows the same graph live.

## Decisions log: important and critical, with the turn
Every decision worth the user's review is one line in `.specs/project/loop/VALIDATE.md`: `- [<slug|general>] turn=<N> level=<important|critical> <doubt> | chose: <choice> | revert: <how>`. `<N>` is the turn you were called with (`--turn N`); stamp it on every line, also the ones the subagents returned (they report the same fields, without `turn`). Only `important` and `critical` are recorded; routine choices (naming, placement inside the pattern, formatting) are not.
- `important`: changes behavior, an API, data, security, a dependency or a feature's scope, or you were unsure and could not verify. E.g. two readings of the spec that both pass; a new library; a changed visible default.
- `critical`: `important` AND hard to revert or risky (data loss, security, public API break, irreversible migration, a scope change the user did not ask for). E.g. a migration that drops a column; a relaxed authorization check; a renamed public route.
- **`level=critical` stops the loop at the end of the turn:** finish the turn as usual (commit what is verified, write `LOOP.json`); after the turn the engine finds the new critical line (it compares against `meta.json` `decisions_mark`, the line count of `VALIDATE.md` before the turn), writes `awaiting_user` with reason `critical decision: <doubt> -> <choice>` for that slug and calls the user. The user answers through the panel (`keep as decided` = keep) or asks for a follow-up stage. Never stop mid-turn, never ask in chat.
- The panel's review marks live in `.specs/project/loop/internal/decisions-review.json` (the app writes it; never touch it).

## Loop settings and the spend cap
The limits of the loop are decided in the planning conversation and written in the ROADMAP header (`references/planning.md`, `references/state.md`): E2E, Dispatch, Max spend per turn, Max spend for the loop (default 50), Max minutes per turn, Branch, Branch base (where worktrees start and the PR target, default developer), Setup, When a feature gets stuck, Push and PR. The panel's start step only shows them, read-only; to change one, the user edits the plan. The engine writes `delivery` (`push_pr`, `remove_worktree_on_finish`), `max_cost_usd` (the per-run cap the user may raise), `cost_warned_at` (the 80 % warning) and `decisions_mark` in `meta.json`. When the cumulative cost reaches the cap the loop goes `paused` with reason `cost cap reached: US$ X of Y` (not `error`): the user raises the limit and resumes. The orchestrator turn runs on Opus (the engine passes `--model opus`), the subagents at Sonnet.

## Follow-up stages
When the user asks for changes after reviewing the decisions, the app appends a stage at the END of the ROADMAP whose heading is `## Stage Follow-up-<n> - Follow-up <n>` (n = 1, 2, ...; e.g. `## Stage Follow-up-1 - Follow-up 1`; the engine takes the stage id from the first word after `## Stage`, so each round needs a unique id), with the same feature-line grammar as any stage (`- [slug] status=pending title="..." ...`). Earlier stages are never edited, renumbered or reopened: a follow-up is new work with new slugs (`deps=` may point at earlier `verified` features). Treat it as the current stage once the earlier ones are closed.

## Non-blocking vs blocking doubt
A one-off doubt (small, reversible divergence) **does not stop the turn**: the orchestrator chooses the conservative path and writes a line in `.specs/project/loop/VALIDATE.md` (`- [<slug|general>] turn=<N> level=<important|critical> <doubt> | chose: <choice> | revert: <how>`). Only a blocking question (access, important business rule, discrepancy, architecture, scope, data, irreversible, PROD, spec vs rule) becomes `awaiting_user`. `VALIDATE.md` appears in the summary, in the completion notification, in the panel and in the PR. Quarantine (`blocked`) only pauses the loop when another feature depends on the blocked one (`--pause-on-blocked` always pauses; `--continue-on-blocked` never). The worktree `../<project>-worktree-loop` belongs to the engine: never create, delete or switch worktree on your own in headless (the manual worktree protocol of `dispatch.md` only applies in interactive mode).

## When testing
`python "<app>/harness.py" loop <repo> --dry-run` shows what it would do without executing anything. `python "<app>/harness.py" summary <folder>` generates the summary at any time, without Claude. Zero-cost suites: `python -m unittest discover -s "<app>/backend/tests" -t "<app>/backend"` (engine and app) and `python -m unittest discover -s "${CLAUDE_PLUGIN_ROOT}/skills/orchestrator/hooks" -p test_guard.py` (guard).

## Permission denied during a turn (only stops when it matters)

`claude -p` returns `permission_denials` when the permission system denies a command. Any denial used to stop the loop with `error`, even when the turn had finished and the agent had redone the step another way (in a real run: a Python block that wrote evidence was denied, while the feature was `verified` and committed). Now `run_loop.py` separates:

| Denial | What the engine does |
|---|---|
| An MCP tool, or a command that looks like `git push`, force, `rm -rf`, `DROP`/`TRUNCATE`/`DELETE FROM`, production (the `GUARD_PROD_HINTS` words) or matches the project's `deny_bash_regex` in `PERMISSIONS.json` | **Stops at once** with `error` ("risky command, not tolerated") |
| An ordinary command (write evidence, read a file, run a local script) and the turn **advanced** (new commit, ROADMAP changed, or stopped asking you) | **Carries on.** Writes one line per denial in `.specs/project/loop/VALIDATE.md` (`- [general] permission denied on turn N (<tool>: <cmd>) | chose: carried on, the turn advanced (<progress>) | revert: check whether what was denied was needed`, long sequences replaced by `***`) and prints a `[loop]` warning. The summary and the PR show `VALIDATE.md` under "For you to validate" |
| An ordinary command and the turn **did not advance** (no commit, same ROADMAP, `continue`) | **Stops** with `error` ("the turn did not advance") |

If the same ordinary command is denied every turn, the `VALIDATE.md` lines show the pattern: adjust the permission or the agent's script afterwards, without the loop having stopped.

## Automatic answer (the engine answers what does not need you)

A text rule in `SKILL.md` ("do not ask about a small dilemma") did not hold: in a real run the orchestrator asked anyway (5 stops in 13 turns, 2 for the same feature, one of them with an option already marked recommended). Now the **engine** guarantees it. When the turn ends in `awaiting_user` with `options` (the quarantine pause included), `run_loop.py`:

1. **Stops and waits for the user** if the question or the options talk about **access** (authorization, credential, secret, password), a **business rule**, a **discrepancy** or inconsistency, real data, production, something irreversible (delete, drop, truncate), `push`, `merge`, deploy, billing or payment, or if there are fewer than 2 options, or if the only option is to abandon. Boundary decided by the user: the agent resolves what is simple and reversible; access, an important business rule and a discrepancy always go to them. The gate tiebreak (below) does not apply either to a feature whose block cites business, discrepancy, access, credential, secret or password.
2. **Otherwise answers on its own**: the option that carries "recommended" (and is not abandoning), or the first one that does not abandon (abandon = end, skip, give up, accept as blocked, cancel).
3. Writes the answer to `ANSWERS.md` marked `[automatic answer from the loop: option N, recommended]` (or `first option that does not abandon the feature`), **writes a line in `VALIDATE.md`** (`- [<feature>] question answered automatically on turn N: "<q>" | chose: option N (<why>): <text> | revert: --answer with another option`) and goes on to the next turn. This also holds at start-up: if the loop was left stopped on a trivial question, running the command again without `--option` already answers and continues.
4. **Ceilings** (to avoid spinning forever, e.g. on a gate that always finds something new): `--max-auto-answers` (12 per run) and `--auto-answers-per-feature` (3). Over the ceiling: stops and waits for the user. `--no-auto-answer` turns it all off.

Answering for the user is still possible at any time (`--option N`, `--answer "..."`, or the panel): the user's answer always beats the automatic one.

## Gate tiebreak (a spec rejected on wording does not hold the feature back)

The `spec-reviewer` may reject the same spec turn after turn on a wording point (marking a case as not covered, adjusting `PATHS`, classifying an `RG-xx`) that the orchestrator itself resolves. In a real run one refactor took **5 rejections** and the loop ended without it, missing only "mark 2 cases as not covered". The real verification is **build + regression**, not the spec's wording. That is why `run_loop.py` breaks the tie:

1. When the loop was about to **finish** (`done`, or all verified/blocked) and there is a `blocked` feature with `note=gate-...` (rejected at the gate), the engine writes an automatic decision to `ANSWERS.md` (question `Gate tiebreak: <slugs> failed the gate several times on spec wording points.`): **approve the spec** (`status=approved`) without redoing the gate, treat the remaining findings as mandatory notes for the executor, and the case that depends on data, a secret or a write that `TEST-ENVIRONMENT.md` does not cover becomes `not-covered` in `regression.md`.
2. Writes a line in `VALIDATE.md` (`- [<slugs>] gate tiebreak on turn N: spec approved without a new gate after several rejections | chose: run with the remaining findings as notes; build and regression decide | revert: --answer asking to redo the gate`) and goes on to the next turn: the executor implements, the `verifier` runs the build and the regression compares with the baseline.
3. **Once per feature** per run (`--gate-tiebreaks`, default 1; `0` turns it off). A feature blocked by an execution or regression failure (not the gate) is never broken: there the problem is in the code and goes to the user. `--no-auto-answer` turns it all off.

## Panel

A local web page that shows the loop's progress and lets the user answer, resume, pause and add notes without typing a command. It is the **Loop Harness panel** (multi-project, a single process; the project's panel at `/p/<id>/`, routes at `/p/<id>/api/...`); contract in `<app>/docs/API.md`; `harness.py serve --project` starts or reuses the app. The routes below (`/api/...`) take the `/p/<id>` prefix.

- **Lifecycle.** After creating/reusing the worktree and before the lock and the turns, `run_loop.py` writes `LOOP-CMD.json`, starts or reuses the panel, prints `[loop] monitor: <url>` and keeps `monitor_url` in `meta.json`. It does not start it in `--check`, `--dry-run` or `--rewind`. `--no-monitor` or `LOOP_MONITOR=off` (in the app's `.env`) turns it off. A failure to start it (app missing, no valid `MONITOR.json` in time, any exception) only prints a warning: the loop continues without the panel.
- **The project's control panel.** The panel is independent of the loop: it starts detached (stdin closed, output in `.specs/project/loop/internal/monitor.log`), **stays up without a loop** and **does not die when `run_loop.py` ends**; the engine never shuts it down. From the front end the user checks (`/api/loop/check`), starts a new loop (`/api/loop/start`), answers, resumes, pauses and shuts down. It only shuts down on `POST /api/shutdown`, on idleness (**loop NOT running, in any state**: `done`, `error`, `stopped`, `awaiting_user` or `no_loop`, and 2 h without use; never while `running`) or if killed from outside. With no live app (including after the automatic shutdown) `python "<app>/harness.py" serve --project <repo>` is enough. A second loop on the same work folder reuses the live panel (live pid and `GET /api/health` with the same `work`).
- **Planning screen.** A project with no approved roadmap that never ran a loop opens in planning mode: a live chat (`/orchestrator plan --headless`, one session resumed per message; `references/planning.md`) that writes PROJECT, RULES, ROADMAP and FLOWS, a preview of them, and the gate checklist. Loop commands, chat, Act and whiteboard refuse with `planning_required` until the user clicks **Approve roadmap**, which needs every gate green (prerequisites, goal, features, fields, no open question, a flow per feature).
- **Roadmap and preflight from the panel.** The checklist ("Where this project stands") walks the user through structure, conformance, codebase map, roadmap (**Generate roadmap** runs `/orchestrator roadmap --headless --goal-file ...`; **Refine roadmap** resumes that session), **Approve roadmap** (writes `ROADMAP-APPROVED.json`), test environment and Check. Every button is the user's click.
- **Loop launched by the panel.** `POST /api/loop/start` runs `run_loop.py` detached with the variable `LOOP_MONITOR_URL=<panel url>`. If it exists and `GET <url>/api/health` answers (only `127.0.0.1`/`localhost`, no proxy), the engine returns that URL (kept in `meta.monitor_url`, which the notification already uses) and does not start another server; if it does not answer, it falls back to the normal behavior (reuse or start). The click on "Start loop" is **the user launching the loop**, which keeps the rule that Claude never launches `run_loop.py`; the orchestrator never calls the `/api/loop/*` endpoints.
- **Panel chat (read-only).** Each agent's Chat tab uses `claude -p` with the `sonnet` model, only `Read`/`Grep`/`Glob`, **no MCP** and up to US$ 1 per answer; it is independent of the loop (does not touch `LOOP.json`, the lock or `ANSWERS.md`) and never changes anything. Product rule: **old version = read-only** (only `Ask`; `Instruct the loop` is disabled and the front end offers "Bring to the current version"); **current version = `Instruct the loop` (default) or `Ask`**.
- **Instruction to the loop.** `Instruct the loop` sends `POST /api/instruction`, which writes to `ANSWERS.md` a `[pending]` block with `Question: (user instruction from the panel)`, an optional `[feature]` prefix and `Attached context:`. The `action` in the response says what happened: `note` (loop running; the next turn applies it), `answer` (loop waiting for you; equivalent to `--answer`) and `note+resume` (loop in `error`, `stopped` or `done`; the panel relaunches the loop, always as the user's click). Without a loop, the panel asks to start one from the New loop panel. In headless the orchestrator treats the block as a user decision; if it asks for a new feature or changes the approved roadmap, the loop stops in `awaiting_user` with the proposal and the options, and does not edit the ROADMAP on its own (`SKILL.md`, Headless mode).
- **Default view.** The panel is **the default view of the loop**: it opens in the browser on its own when the loop starts (only when the server starts; reusing a live panel does not reopen it), the URL goes in every notification, and it is where you follow, answer, instruct, chat, act and deliver. `LOOP_MONITOR_OPEN=off` (environment or the app's `.env`) turns off only the browser opening; `--no-monitor` (or `LOOP_MONITOR=off`) turns off the whole panel. The orchestrator, when handing over the loop command, always tells the user this.
- **Act mode (current version).** Runs objective actions from a **whitelist**, done by code (not by the AI), always with the user's **explicit confirmation**: `deliver` (push **only the feature branch** + PR to the integration branch, via `harness.py deliver`), `summary` (`harness.py summary`, same output folder), `push` (feature branches, no PR) and `clean_worktrees` (backup first). Free text goes through a router (`claude -p` haiku, no tools) that can only pick an action from the list; outside it becomes `none` and the front end offers to send it as an instruction. Act **does not reopen the loop**. Push and PR only exist through delivery: the guard and the hard rules still hold, and delivery refuses a protected branch, force and an open feature; that is why `deliver` from the panel only works with the loop stopped and no open feature. The click on confirm is the user authorizing; the orchestrator/Claude never calls `/api/action/*`.
- **Signal files in `.specs/project/loop/`.** `json/MONITOR.json` (the app writes it when registering the project and deletes it on shutdown: pid, port, absolute URL of the project's panel, repo, work); `json/LOOP-CMD.json` (`run_loop.py` writes it on every run: `argv` and `cwd` to relaunch, **without** `--answer`/`--option`); `internal/PAUSE` (the panel creates it; an empty file).
- **PAUSE.** At the top of each turn the engine checks the file: if it exists, it deletes it, rewrites `LOOP.json` as `awaiting_user` and ends with the reason "paused by the user in the panel; click Resume in the panel or run the command again" (next: "resume when the user wants"). It does not spend a turn. The turn in progress ends first (PAUSE is only read between turns).
- **Relaunch from the panel.** Answering or resuming in the panel runs the `argv` of `LOOP-CMD.json` detached (with `--answer "<text>"` when it is an answer). It is the user launching the loop, not the orchestrator.
- **Security.** Listens only on `127.0.0.1` (a free port from 47800 to 47899), rejects a foreign `Host` (DNS rebinding), every `POST` requires the `X-Monitor-Token` header (a random token generated on every start, only in memory, injected into `index.html`) and nothing returns `.env`, credentials or the raw `guard.log`. The guard also blocks any agent, the orchestrator included, from calling the user-click endpoints (`panel-trigger`) or reading `~/.loop-harness/app.json` (`secrets`).
- **Notification.** `monitor_url` enters the notification context and appears in every channel; in "How to continue" it becomes the panel mode ("answer in the panel: <url>"). A standalone notification from the chat (`harness.py notify --subject/--body`) does not change.
